# Meridian Product Boundary Rules

These rules prevent Meridian from drifting into adjacent categories.

## What Meridian IS

A focused release convergence intelligence workflow that answers:

1. What is actually running?
2. What combinations were actually validated?
3. What combination exists now that was never validated?
4. What undocumented contract governs that connection?
5. Can we safely execute the missing compatibility check?
6. Where is the First Demonstrated Divergence?
7. What evidence supports the result?

## What Meridian is NOT

Do not describe or build Meridian as:

- An observability platform
- A monitoring dashboard
- An AIOps platform
- A generic root-cause analysis system
- A generic release-readiness scorer
- A deployment orchestrator
- A rollback engine
- A generic environment-drift tool
- A generic contract testing product
- A software delivery knowledge graph
- A generic CI/CD product
- A generic AI coding assistant
- A generic RAG chatbot

## Positioning Language

Use:
> **Actual composition + validation evidence + implicit contract discovery + executable rehearsal.**

Avoid:
- "AI-powered release safety" (too generic)
- "AI-powered" as a standalone claim
- "risk score" (implies a made-up number)
- "guaranteed safe" (no deployment tool is guaranteed)
- "root cause" (use "First Demonstrated Divergence")
- Made-up confidence percentages
- Fake ML scores

## Differentiation Reminder

The defensible novelty is the **specific combination**:
- Reconstruct actual environment composition from promotion history
- Identify exact version combinations that lack validation evidence
- Discover implicit integration constraints from deployed code + enterprise documents
- Resolve untested boundaries through isolated executable probes (not LLM opinions)
